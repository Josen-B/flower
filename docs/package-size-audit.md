# Flower 完整离线包体积审计

用户要求在保留功能和性能的前提下缩小安装器，并明确保留完全离线安装。
不改成首次联网下载，不删减AI或分类词库，不降低模型精度或运行期编译优化级别。

删许可或来源文档不能带来与其展开体积相同的下载收益，也不属于本轮方案。

## 同载荷无损压缩实验

以同一已验证ZIP、151个相同载荷文件构建，runner逐文件比对了暂存字节。
保留SolidCompression，不运行安装器，不修改注册或输入法状态。

| Inno设置 | EXE字节 | 相对原EXE节省 | 解压字典内存估计 |
| --- | ---: | ---: | ---: |
| lzma2（默认max） | 65,154,907 | — | 8MiB |
| lzma2/ultra64 | 64,872,757 | 282,150（0.433%） | 64MiB |

ultra64实际ISCC编译53.438秒；默认基线复用既有制品，没有为比较重复构建。
内存为官方算法估计，不是实测安装器总峰值；没有执行安装或测量安装耗时。
该候选没有采用：节省较小且增加解压字典内存。未继续盲测更大字典。

补测 `lzma2/ultra64` 配合显式 `LZMADictionarySize=8192`，仍保持约8MiB解压字典：
实际EXE为65,154,898字节，只比基线少9字节，ISCC编译46.94秒。
151个暂存载荷文件仍与原ZIP逐字节一致，未使用下述编译精简候选的PE。
这9字节差异没有定位到压缩流或容器元数据，不能称编码器优化收益，因此不采用。
官方默认参数中max与ultra64的FastBytes均64、MatchFinder均BT、Algorithm均1；
不能把ultra64名称误解为这些编码参数同时提高。

官方参数说明：
https://jrsoftware.org/ishelp/topic_setup_compression.htm
https://jrsoftware.org/ishelp/topic_setup_lzmadictionarysize.htm

## 编译精简的验收边界

仅考虑同源release的全程序链接和符号精简，保持opt-level=3及panic=abort，
不使用偏向体积的s/z优化、不启用本机专属CPU指令。
模型、运行库、词库和许可逐文件比对；固定lexicon_probe交错比较原版与候选版，
按首次进程内加载、暖查询及按键负载分别记录，系统缓存不冒称真实磁盘冷启动。
只有实际缩小且未见性能退化的候选才进入正式构建。

同源候选使用fat LTO、codegen-units=1、strip=symbols，保持opt-level=3和panic=abort。
实际rustc参数表明fat LTO用于两个EXE及probe；同时生成cdylib/rlib的库没有fat LTO参数，
因此不将其描述为三个PE均启用全程序LTO。

## 推理运行库裁剪的边界

固定模型原始图为opset11、1201个节点、21种算子。原始图算子列表不是安全裁剪终点：
运行时优化可能生成融合节点，必须保留适用融合及CPU/MLAS性能路径。
固定ORT v1.20.0的非minimal `--include_ops_by_config` 源码构建可研究，
但目前没有经过验证的候选DLL或缩减/性能结果。
该版本minimal构建不支持当前ONNX格式，需要ORT格式且有优化能力限制，
不能直接替换现有加载路径来满足本任务。

本次定向核查的Microsoft官方v1.20.0发布列表没有现成reduced Windows x64 CPU C API包。
定制构建还需要原生第三方依赖和长期可重建维护；没有安装依赖、下载完整构建树或编译ORT，
不将编译工具存在视为候选可用，也不猜测DLL会省多少。
该运行库在ZIP中约4.37MB的贡献仅是局部优化的上限尺度，不是预计节省量。

## 本轮结论

已测三种候选没有值得采用的安装器瘦身收益，因此保留0.4.13正式包和原构建配置，
不为9字节或以增加解压字典内存换取0.43%的结果发布新版。
本轮新增的是审计与实验记录，没有删功能、词库、模型、许可证或改成联网安装。
不将这个结论扩大为“所有进一步优化都不可能”；定制推理运行库尚未完成构建及性能验收，
不能冒充已验证且保证无退化的现成方案。
